01

The philosophy

Practices change slower than tools.

Without Hone

Entropy creeps in silently

  • Methods grow to 200 lines, nobody notices.
  • Magic number 86400 appears in 7 files.
  • Test called test1 passes but tests nothing useful.
  • Same validation logic copy-pasted across 4 services.
  • Class called DataManager manages everything.

With Hone Skills

Caught at the source

  • OrderService.process() is 187 lines — split at natural seams.
  • 86400 → named constant SECONDS_PER_DAY in 7 locations.
  • 12 tests fail naming audit — rewrite as behavior sentences.
  • Validation pattern duplicated 4× — extract to shared/validate.
  • DataManager → OrderFetcher, InventoryCalculator.

Concrete. Timeless. Actionable.

silent decay scheduled vigilance

06

Frequently asked

For engineers who value craft.

Where do these practices come from?

From 25 timeless software engineering practices compiled at the XTC meetup and documented on darkcoding.net. These practices emphasize that good engineering judgment changes much slower than tools — and is typically a better investment.

Does it work with any language or framework?

Yes. Skills are language-agnostic and adapt to whatever tooling your repo already uses. They read your code structure, not a config file.

How is this different from linters?

Linters check syntax and style rules. Hone skills reason about your code — finding methods that grew too long, naming that lost its meaning, duplication that crept across services, and entropy signals that tools miss.

Can I run these on a schedule?

Absolutely. Each skill is designed for recurring use. hone:broken-windows-hunt runs daily, hone:test-naming-audit on every PR, and most others weekly. Output formats support comparison across runs.

Where should I start?

Run hone:broken-windows-hunt for a quick entropy snapshot, or hone:method-brevity-audit for a deeper structural audit. Both produce immediate, actionable results.
